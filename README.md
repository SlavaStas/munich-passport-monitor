# munich-passport-monitor

Проверяет электронную очередь ДП «Документ» в Мюнхене для услуги «Закордонний паспорт та (або) ID-картка». При появлении доступных даты и времени отправляет сообщение в Telegram. Запись оформляет сам заявитель. Скрипту не нужны паспортные данные, номер телефона, Дія или банковская сессия.

[Форма очереди](https://munich.pasport.org.ua/solutions/e-queue) · [Запуски GitHub Actions](https://github.com/SlavaStas/munich-passport-monitor/actions/workflows/check-appointments.yml)

## Запуск в GitHub

1. В этом репозитории уже есть workflow. Для собственной копии создайте публичный репозиторий через **GitHub → New repository** и загрузите весь проект, включая `.github/workflows` и lockfile, или сделайте Fork. В форке включите Actions. Для запуска автоматической проверки при публикации в ветку с именем, отличным от `master`, измените фильтр `push.branches`. Расписание использует основную ветку репозитория.
2. В Telegram откройте официальный [@BotFather](https://t.me/BotFather), отправьте `/newbot`, задайте имя и username. Скопируйте выданный токен. В личном чате с созданным ботом нажмите **Start** и отправьте любое слово.
3. Узнайте ID личного чата. На своём компьютере выполните команду ниже и введите токен в скрытом приглашении. Она выводит только ID личных чатов. Используйте свежего бота без webhook и других обработчиков, чтобы обновление было доступно. Если список пуст, отправьте боту новое сообщение и повторите команду.
4. В **Settings → Secrets and variables → Actions → New repository secret** добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Храните оба значения в Secrets. Проекту не нужен файл `.env`.
5. В **Actions → Munich passport appointments → Run workflow** выберите основную ветку и режим `dry-run`. Команда проверяет сайт, печатает результат, не обращается к Telegram и не меняет состояние.
6. Для проверки доставки вручную выберите `telegram-test`. Он отправит одно помеченное тестовое сообщение. Проверьте его в чате. Режим `monitor` выполняет рабочую проверку, в том числе запись состояния и отправку новых мест.
7. Откройте запуск в **Actions**, затем job и его последний шаг. Строка JSON содержит услугу, статус и найденные слоты либо краткую причину ошибки. Успешный тест Telegram и успешная проверка очереди проверяют разные части сервиса. До добавления обоих секретов рабочий запуск проверяет очередь и сохраняет подтверждённый результат, но отмечает ошибку настройки доставки.

```sh
python3 - <<'PY'
from getpass import getpass
from json import load
from urllib.request import urlopen
from urllib.error import URLError
token = getpass("Токен BotFather: ").strip()
try:
    with urlopen("https://api.telegram.org/bot" + token + "/getUpdates", timeout=15) as r:
        updates = load(r)["result"]
    chats = [item.get("message", {}).get("chat", {}) for item in updates]
    print(sorted({c["id"] for c in chats if c.get("type") == "private"}))
except (URLError, ValueError, KeyError):
    print("Не удалось получить обновления. Проверьте токен и настройки бота.")
PY
```

## Как определяется результат

Playwright открывает публичную форму в чистом headless Chromium, проверяет заголовок мюнхенского центра и выбирает услугу по её украинскому названию. Сетевые запросы отправляет JavaScript самой страницы. Скрипт читает ответ и сверяет его с формой. Он не отправляет форму записи. Отдельный официальный API для внешних наблюдателей при исследовании не найден.

| Статус | Условие |
| --- | --- |
| `AVAILABLE` | Получены разрешённые даты и время с `isAllowed === true`. Значения и подписи совпали с вариантами в видимых списках формы. |
| `UNAVAILABLE` | Сайт ответил распознаваемым списком без разрешённых дат, и форма явно показала сообщение о занятых местах. При наличии дат это же условие проверяется для времени каждого дня. |


При отказе доступа, неполной загрузке, ошибке HTTP или расхождении данных проверка завершается с кодом 1 и записью `check: failed`. Поле текущего статуса отсутствует. В рабочем режиме `lastConfirmed` содержит дату и результат последней подтверждённой проверки либо `null`, если сохранённого подтверждения нет. Успешный ответ помечен `check: confirmed` и содержит время, источник и основание вывода.

После выбора услуги форма делает запрос дней. Скрипт сверяет идентификатор выбранной услуги и тип запроса, а при запросе времени также дату. После выбора доступной даты она запрашивает время. В текущей форме нет отдельного стабильного ID талона, используем ключ из даты и времени для этой услуги и центра. Если формат времени изменится, проверка завершится с ошибкой. Синтетические положительные ответы используются только в тестах.

19 ноября 2026 года при исследовании форма вернула структурированный пустой список дней и явно сообщила, что места заняты. При одном из последующих запусков проверяющего скрипта получен HTTP 429. Положительную ветку удалось проверить на локальной модели формы. Первый живой ответ с доступным временем предстоит проверить по логам. Сервис сообщает, что показал сайт данному браузеру в момент проверки. Место может исчезнуть и до перехода по ссылке.

## Состояние и доставка

Отдельная ветка `monitor-state` создаётся при первом рабочем запуске. В ней только `state.json` и история изменений. В публичном репозитории они видны всем. Там хранятся ключи уведомлённых слотов, число последовательных сбоев, время диагностики и при необходимости срок ожидания. При каждой подтверждённой проверке записываются её время и результат. Идентификатор чата и токен туда не записываются.

- Кэш зависимостей служит для ускорения установки. У кэшей и артефактов ограничен срок хранения. Ветка позволяет следующему запуску прочитать точное состояние и сохранять его обычным fast-forward push. Для неё требуется право `contents: write`. Защита ветки должна разрешать запись от Actions. Не удаляйте и не редактируйте её во время работы.
- Повторная проверка тех же слотов молчит. После подтверждённого исчезновения ключ удаляется. Если слот появился снова, приходит новое уведомление. При неудачной проверке набор ранее уведомлённых слотов сохраняется. Неполная проверка, например сбой на второй дате, отклоняется целиком.
- Общая группа `concurrency` сериализует рабочие и ручные запуски. Каждая партия сообщений подтверждается отдельно. Новый слот попадает в состояние только после ответа Telegram с `ok: true` и `message_id`. Сбой доставки или сохранения делает запуск красным. При потере ответа Telegram или сбое между успешной доставкой и push возможен дубль. У Bot API и Git нет общей транзакции.
- После трёх подряд неудачных проверок бот отправляет диагностику, далее не чаще раза за 24 часа до восстановления. Подтверждённая проверка сбрасывает счётчик. Если сломался сам Telegram, GitHub, установка пакетов или сохранение состояния, причину смотрите в Actions.
- Для временного сетевого сбоя или 5xx предусмотрена одна повторная попытка через две секунды. При запрете доступа, CAPTCHA или 429 проверка прекращается. При 429/503 с действительным будущим `Retry-After` рабочий режим сохраняет срок и пропускает запуски до его истечения. Для Telegram короткий явный `retry_after` учитывается один раз. Сетевой таймаут доставки оставляет сообщение неподтверждённым.
- Таймаут одной операции формы — 18 секунд, перехода на страницу — 30 секунд, проверки в браузере — 2 минуты, workflow — 8 минут. Неподтверждённый ответ, сбой конфигурации, отправки или записи возвращают ненулевой код. Явное ожидание до `Retry-After` выводится отдельной строкой в лог.

## Расписание, стоимость и отключение

В `.github/workflows/check-appointments.yml` задано `*/15 * * * *` (UTC), то есть на 00-й, 15-й, 30-й и 45-й минутах каждого часа. Например, `17 * * * *` означает раз в час на 17-й минуте. Для сообщения время проверки форматируется в Europe/Vienna. GitHub может задержать или пропустить запланированный запуск, а слот может открыться и закрыться между проверками. По правилам GitHub расписание публичного репозитория может отключиться после 60 дней отсутствия активности. Текущий статус виден во вкладке Actions.

Стандартный GitHub-hosted Linux runner в публичном репозитории доступен бесплатно. Для приватной копии расходуется квота аккаунта. При 96 запусках в день расход за 30 дней составит 2880 запусков, поэтому бесплатность приватной копии зависит от продолжительности и доступных минут. Для отключения откройте **Actions → Munich passport appointments → … → Disable workflow**. После повторного включения ветка состояния используется снова.

## Локальная проверка

Node.js 26 LTS, npm и Git. Установите зависимости и браузер, затем выполните проверки. В Linux при отсутствии системных библиотек используйте `npx playwright install --with-deps chromium --only-shell`. Для уже установленного совместимого Chromium можно передать путь в `CHROMIUM_EXECUTABLE`.

```sh
npm ci
npx playwright install chromium --only-shell
npm run typecheck
npm run lint
npm test
npm run test:browser
npm run build
npm run check
```

Последняя команда обращается к реальной очереди один раз. Остальные тесты используют локальные ответы, временный Git-репозиторий и замоканный Telegram. В workflow установка зависимостей кэшируется средствами setup-node. Браузер запускается без сохранения сессионных данных между проверками.
